# 功能開發批次工作法

## 這個skill為什麼存在

多階段功能（新的決策邏輯、新的狀態機、需要人工確認才生效的流程）如果一次全寫完再測，出問題時很難定位是設計錯了還是接線錯了；如果邊寫邊接真實資料/UI，又容易在還沒確認核心邏輯正確前就把時間花在跟本質無關的問題上（環境設定、UI排版）。這個skill記錄一套已經在實際專案裡走過、成功交付一整套多批次功能的節奏：**先把核心邏輯完全隔離出來，用手造資料證明它對，再往外接真實資料，最後才做UI**。

## 批次節奏

### 1. 契約批次（不寫程式碼）

大型/有風險的功能，開工前先把設計寫成文字提案（架構、命名、跟既有系統的邊界、資料要不要版本化），拿到明確核准才動手。這不是形式主義——邊界一旦在提案階段就談攏（例如「這是獨立的外部模組，不改動既有核心邏輯，不覆寫既有欄位」），後面所有實作都會依循這個邊界，不會做到一半才發現要推翻設計。

### 2. 只讀調查批次（不寫程式碼）

動手前先確認需要的資料/介面缺口在哪裡（現有資料的粒度夠不夠、有沒有現成的查詢方法可以重用）。調查結果先單獨記錄下來，不預先寫程式碼——讓調查結果本身可以被審查、核准範圍，而不是跟著程式碼一起被動接受。

### 3. 沙盒批次：先把核心邏輯的正確性談對，不碰真實資料/DB/UI

這是整套節奏裡最關鍵的一步。核心邏輯（判斷條件、計算公式、狀態轉換規則）先寫成**不碰網路、不碰資料庫、不呼叫外部服務**的純函式，輸入是手造的測試資料，輸出直接斷言。

**動手寫測試資料前，先自己手算一次預期結果，再去對答案**——這比寫完程式碼才回頭想測試案例更容易抓到設計本身的問題。真實案例：某個「箱型突破」判斷把當天自己的高點也算進了箱型上緣，導致「收盤突破箱型」邏輯上永遠不可能成立；另一個案例是「量縮」和「爆量」兩個條件原本都比較同一天的成交量，邏輯上互相矛盾——這兩個都是在手算測試資料、核對預期數字的過程中發現的，不是跑測試後才抓到的。跑測試只能抓到「程式碼跟你寫的測試不一致」，抓不到「你的測試本身跟你的設計一起錯了」。

如果邏輯用到彈性欄位（JSON/JSONB之類）存快照或參數，用固定形狀的schema（例如語言內建的資料類別/型別），不要用自由格式的字典——形狀在結構層面就鎖住，比只靠慣例維持一致性可靠。

如果這個邏輯之後會需要「人工確認才算數」的關卡，現在就決定好用**只新增、不覆寫**的紀錄設計（append-only事件/日誌），不要用「一個可變的目前狀態欄位」。這個決定要在沙盒批次就定下來，因為它會決定後面所有讀寫邏輯的形狀，事後改的成本很高。

### 4. 真實接線批次：把純函式接上真實資料/DB/端點

沙盒邏輯確定沒問題後，才寫「讀真實資料、算出結果、寫回」的整合層。這一步常見的坑：
- **同一次觸發的重複執行要有守門**：如果這個流程可能被重複觸發（人工重試、排程重跑、使用者連點兩下），要用資料本身的識別欄位（例如它所依據的那筆輸入資料的日期/版本），不要假設「這個流程一次只會被觸發一次」。
- **同一輪處理裡插入多筆紀錄，排序不能只靠系統時間巧合遞增**：如果一次呼叫要新增兩筆以上、彼此有先後關係的紀錄，而後續查詢是靠時間戳排序取最新一筆，用同一個時間戳給多筆紀錄會讓排序在儲存層面不保證正確——真實案例是因此讓查詢抓到了錯的那一筆（有失敗的端到端測試證實）。要嘛讓後插入的紀錄時間戳明確晚一點，要嘛換一個不依賴時間戳的排序依據。

### 5. UI批次：人工確認關卡＋端到端驗證

最後才做前端UI，而且如果這個功能牽涉「輸出要人工確認才算數」的約束，UI必須包含一個明確的確認動作，按下去要**真的**呼叫後端、真的寫進儲存層，不能只是前端state假裝改變。驗證方式：實際啟動整個系統（不只是看程式碼），手動塞入一筆資料、操作UI、再從後端查詢確認狀態真的變了——不是只看畫面看起來對就結案。

## 開工前的固定檢查

- **先查有沒有現成的基礎設施，再動手蓋新的**：準備新增一個排程/服務/整合前，先查現有設定裡有沒有已經存在但沒人記得的東西，不要預設「目前完全沒有」。真實案例：整個功能系列開發期間，所有協作者都以為某個排程完全不存在，結果專案owner早就設好了，只是沒寫進交接文件——直到準備寫新排程檔案時才發現，差點做了一段重複的邏輯。
- **新增路由/模組後，用工具查一次實際註冊結果，不要只看程式碼**：很多語言允許同名模組互相覆蓋匯入而不報錯。真實案例是兩個路由模組用了同一個裸名匯入，其中一個的路由整批沒有註冊成功，且完全沒有錯誤訊息——改完之後呼叫框架自己的內省機制（例如列出所有已註冊路由）確認預期的都在、沒有互相覆蓋，比事後才發現「端點打不到」便宜很多。
- **合併回主分支前，先確認自己的分支有沒有落後**：如果有其他協作者可能直接推主分支，push前先跟主分支比對，落後時不要無腦force-push蓋過去（那需要使用者明確同意，而且可能丟失別人剛做的修正）——改用merge，衝突時逐一核對兩邊內容，確認沒有丟失任何一邊有意義的變更。

## 一頁式檢查清單

- [ ] 大型/高風險功能有沒有先提案並拿到明確核准，才動手
- [ ] 核心邏輯有沒有先寫成不碰網路/DB的純函式，用手算過的測試資料驗證
- [ ] 需要人工確認才算數的狀態，有沒有用append-only設計，而不是可變狀態欄位
- [ ] 動手接真實資料前，有沒有查過同名的既有基礎設施/路由，避免重工或撞名
- [ ] UI的「確認」動作有沒有真的呼叫後端、真的寫進儲存層，並且啟動整個系統端到端驗證過（不是只看畫面）
- [ ] push前有沒有先跟主分支比對，落後時用merge而不是force-push
